## Desktop XR: headset-first Play and Simulator reliability

**Request.** The developer asked for a way for both the developer and Claude to test without toggling **Disable Experimental Preview**, to protect the tracked OpenXR settings if Unity crashes, and to find why Claude's Simulator runs failed. The target is a standalone Quest 3 build, with most testing over Quest Link; `CLAUDE.md` and `HeadsetChecks.md` now say so.

**Change.** `DesktopXrTools.cs`: normal Play uses the system runtime (Quest Link). **Play in Simulator** runs Meta Core's own Simulator toggle (**Meta > Meta XR Simulator > Activate**) if it is off. It adds the Operator layer and makes a one-shot Play request that expires after 30 seconds. When Play stops, it removes the layer and turns the toggle back off. **Disable Experimental Preview** and the project's separate Simulator path were removed. The Operator configuration now takes only the Operator JSON. The layer is changed in memory only, and the helper clears the dirty flag it causes. On load and on leaving Play, the helper removes the layer from the tracked settings file if present. `ProjectSettings.asset`: **Run In Background** changed from off to on; Android ignores this setting. Play in Simulator refuses to start while it is off. `DesktopXR.md` and the `xr-preview` skill were updated.

**Cause found.** With Run In Background off, Play started while Unity was not the focused window froze after two frames. Claude's runs always start this way; the developer clicks Play inside Unity. The Simulator reached SYNCHRONIZED, but Unity processed no events, `GfxDevice::UpdateBufferRanges` errors repeated, and one run crashed the Editor. Before the fix, Claude's runs after Quest Link failed 4/4, with and without the Operator. That led to a wrong Link-related theory and a restart guard, which has been removed. Why some earlier background runs worked is unexplained.

**Checks.** The in-memory layer change was confirmed: during Play the feature was not dirty, and the file had no Operator entry. For the repair check, the layer was saved into the settings through Unity. The load routine removed it and left the file identical to the commit. After the Run In Background change, the post-Link Editor session that had failed was retested with Unity unfocused. Meta toggle only reached FOCUSED, with frames advancing and the head tracked at 1.7 m. Play in Simulator with the Operator reached FOCUSED; an Operator-set right grip and trigger were read back exactly in Unity, then released. After the guard was removed and the code compiled, the final Play in Simulator run reached FOCUSED with frames advancing. No new graphics errors appeared in any fixed run.

**Observed issue.** Stopping that final run crashed Unity during Operator teardown. The last line was `Destroying Agentic MCP Server...`; there was no crash dump or Windows error record. Each of the four earlier teardowns in that Editor session blocked Unity for about 13 seconds before `AgenticLayerXrDestroyInstance succeeded`. This teardown is inside Meta's Operator binary. The tracked OpenXR settings stayed clean through the crash. The log was preserved at ignored `Logs/DesktopXR/editor-crash-2026-09-19-1836.log`.

**Human feedback.** The developer confirmed normal Play on the Quest 3 over Link without toggling. The developer's manual Meta-toggle Simulator runs worked. **Stop-method retest.** In the crash, Play was stopped through Unity MCP `manage_editor stop`, so the 13-second Operator teardown ran inside a pending MCP command, which timed out. The developer asked for at least five Play/stop cycles. In a reopened Editor, Claude ran five Play in Simulator cycles.
